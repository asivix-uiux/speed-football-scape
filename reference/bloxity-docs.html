Bloxity SDK

One drop-in SDK for cross-game identity. Add Bloxity login, avatars, friends & presence, synced settings and Bux in-game currency to any HTML5 or Unity WebGL game — embedded on bloxity.io or standalone on your own domain.

🔐 Auth  cross-game login + JWT 👕 Avatars  equipped cosmetics & body 👥 Social  friends, presence, invites ⚙️ Settings  portal-synced 💰 Bux  server-authoritative IAP

The SDK is published globally as window.Legion.SDK (the platform was formerly called Legion — the package and namespace keep that name; the product is Bloxity). It works two ways automatically:

  • Embedded — your game runs in an iframe at bloxity.io/g/<your-slug>. Auth, friends and purchases flow through the portal over postMessage (no extra HTTP).
  • Standalone — your game runs on your own domain. The same calls fall back to the Bloxity REST API at api.bloxity.io and a login popup window.

You write the same code for both — the SDK detects its environment and routes accordingly.

What happens when your game boots (the handshake)

Almost every "why doesn't the SDK work?" question comes down to timing — calling something before the data it needs has arrived. Here is the exact boot sequence when your game is embedded on bloxity.io, so you know precisely when each piece of data is ready:

  1. The portal opens your game in an iframe t = 0

    A loading overlay is already covering your game. The portal is waiting to hear from your code.

  2. The SDK script loads <script> onload

    window.Legion.SDK now exists. Nothing before this point can touch the SDK, so put your integration code after the script tag (or in its onload).

  3. You call Legion.SDK.init() you, once

    The SDK immediately posts a handshake request and an auth request to the portal, then returns. init() is synchronous and returns before the portal answers — at this instant getUser() is still null.

  4. Your onUserChanged / settings.listen callbacks fire once immediately microtask

    They fire right away with the current (empty) state: onUserChanged with null, each settings.listen with its default value. This is why you subscribe first and let the callback drive everything — it will fire again with real data.

  5. The portal answers with the handshake ~1 round-trip

    One reply carries everything at once: the logged-in user (or null for a guest), the access token, the equipped avatar, the resolved gameSlug, the debug flag, and the current settings. The SDK stores it all and fires your callbacks again — onUserChanged (now with the real user), avatar.onAvatarChanged, and every settings.listen — with the real values.

  6. Your game finishes its own loading, you call loadingEnd() you, when ready

    The overlay lifts and the player is in. (See Game lifecycle for the loading-screen rules.)

The three timing rules that prevent 90% of bugs. (1) Never read getUser() right after init() and assume it's populated — it isn't yet. Drive your UI from onUserChanged, which fires again when the user arrives. (2) There is no timeout on the handshake; if the portal is slow, your callbacks simply fire later. Subscribe before you need the data, not after. (3) Register your settings.listen() keys and your onUserChanged subscription immediately after init(), before loadingEnd(), so the first push from the portal isn't missed.

Standalone (your own domain) is simpler: init() reads a saved token from localStorage, drops it if expired, and calls GET /v1/auth/me to refresh the user. No iframe, no postMessage, no portal. onUserChanged fires with null, then again with the restored user once that request returns (or stays null if there's no valid token).

Quick start #

The smallest working integration — log a user in and react to login state:

html
<script src="https://sdk.bloxity.io/legion-sdk.min.js"></script>
<script>
  // 1. Initialize once. gameSlug is the slug your game is registered under
  //    on bloxity.io (required for Bux purchases; auto-filled when embedded).
  Legion.SDK.init({ gameSlug: 'my-game' });

  // 2. React to login state. Fires immediately with the current user
  //    (or null), then again on every login / logout.
  Legion.SDK.auth.onUserChanged((user) => {
    if (user) {
      console.log('Hello', user.displayName || user.username);
    } else {
      console.log('Not logged in');
    }
  });

  // 3. Open the login UI (auto-picks modal vs popup) from a button.
  document.getElementById('login').onclick = () => Legion.SDK.auth.showAuthPopup();
</script>

Authentication #

The SDK manages an access token (JWT) and the current user. User objects are never cached — only the token is persisted (localStorage["legion_token"]) and fresh user data is re-fetched on load. The golden rule of auth here: you never poll for the user — you subscribe with onUserChanged and let it drive your UI. It fires once immediately with the current state and again on every login/logout, so a single subscription is your complete auth state machine.

Add login in five steps

  1. Initialize once, on load

    Legion.SDK.init({ gameSlug: 'my-game' }).

  2. Subscribe to onUserChanged — your single source of truth right after init
    javascript
    Legion.SDK.auth.onUserChanged((user) => {
  if (user) showLoggedIn(user);   // render name/pfp, load friends + balance
  else     showLoginButton();     // show a "Log in" button
});
  3. Wire your "Log in" button to showAuthPopup() on click

    loginBtn.onclick = () => Legion.SDK.auth.showAuthPopup();. You don't need its return value — the login flow ends by firing onUserChanged, which your step-2 handler already catches.

  4. Wire "Log out" to logout() on click

    Legion.SDK.auth.logout() clears the token and fires onUserChanged(null) — again, your handler does the rest.

  5. (If you have your own backend) verify the identity server-side when user arrives

    Inside the user branch of step 2, call authenticateWithServer(yourUrl) (see below) and use the session it returns.

Authenticate with your own game server

If your game has its own backend, validate the Bloxity identity server-side. The SDK POSTs { token, user } to your endpoint; you verify the JWT and return your own session.

Legion.SDK.auth.authenticateWithServer<T>(serverUrl: string) => Promise<T | null>both
What
Hands the Bloxity identity to your backend so it can mint its own session. The SDK sends POST serverUrl with Content-Type: application/json and body { token: <bloxity JWT>, user: <full user object> }. (No Authorization header — the token is in the body.)
Call
const session = await Legion.SDK.auth.authenticateWithServer('https://yourgame.com/api/legion-auth').
Returns
Promise<T | null> — your server's parsed JSON response on 2xx, or null if there's no logged-in user, the request fails, or the response isn't OK. Repeated calls to the same URL are de-duplicated (one in-flight request is shared).
Why
Only needed if your game keeps its own accounts/inventory. Your endpoint verifies the Bloxity JWT, upserts a local user keyed by the Bloxity id, and returns your own tokens — so the rest of your game talks to your backend, not Bloxity's.
When
Inside your onUserChanged handler, in the branch where user is non-null (and again is a no-op-safe retry if you call it more than once quickly). Skip it entirely if you have no backend — just read getUser().
Live

Guests (signed-out players)

Not everyone logs in — but you should never show an anonymous "Player 1". When getUser() is null, Legion.SDK.auth.getGuest() gives the signed-out player a stable, friendly identity: a Bloxity-generated name (e.g. "Comet42") and a derived profile picture. The name is minted once and saved to localStorage, so the same browser keeps the same guest name across sessions.

javascript
// One line that ALWAYS gives you someone to display:
const player = Legion.SDK.auth.getUser() || Legion.SDK.auth.getGuest();
nameLabel.textContent = player.username;    // "coolplayer42"  or  "Comet42"
avatarImg.src      = player.pfp;         // real PFP or the guest's derived PFP

// Distinguish the two if you need to (e.g. gate a feature behind login):
if (player.isGuest) promptLoginForRankedMode();

Avatar / cosmetics #

A player's Bloxity avatar is a set of equipped item IDs — a hat, a back item, a skin texture, and per-body-part meshes — plus body proportions (height, arm length, etc.). Your job as a game is to read those IDs, load the matching meshes/textures from the CDN, and re-load them when the player changes something so their character looks the same in your game as it does on their profile. Everything here is read-mostly; the portal owns buying and (in standalone mode) the SDK can show a customizer.

Show the player's avatar — the recipe

  1. Read the equipped IDs after login/handshake

    const eq = Legion.SDK.avatar.getEquipped(); — gives you every slot at once.

  2. Turn each ID into a CDN URL, skipping empty slots per slot

    An ID of '-1', '', 'undefined' or null means "nothing equipped — use the default mesh baked into player.glb". Only build a URL for real IDs. Base is https://static.bloxity.io/avatars; the exact patterns are in CDN asset URLs.

    javascript
    const CDN = 'https://static.bloxity.io/avatars';
const real = (id) => id && !['-1', 'undefined'].includes(id);

if (real(eq.hatId)) loadMesh(`${CDN}/items/hats/${eq.hatId}.obj`,
                             `${CDN}/textures/hats/${eq.hatId}.png`);
if (real(eq.hairId)) loadMesh(`${CDN}/items/hats/${eq.hairId}.obj`,   // hair shares the hat folders and anchor
                              `${CDN}/textures/hats/${eq.hairId}.png`);
// Skin with any worn face / pants already drawn on it
loadSkin(Legion.SDK.avatar.getSkinTextureUrl());

    Neck, chest, waist and hand accessories load the same way from /items/{neck|chest|waist|hand}/{id}.obj; where to attach each one is in CDN asset URLs.

  3. Subscribe so the character updates live once, at startup

    onAvatarChanged fires whenever the player equips/unequips (in the portal or the in-game customizer); onProportionsChanged fires on body-slider changes. Re-run your load/rescale logic inside them so the change shows up without a reload.

Synced settings #

Players change settings in the Bloxity portal's in-game pause menu (volume, graphics quality, sensitivity…), and the SDK pushes those values into your game. Every value is a string — "80", "High", "true" — so parse as needed. You don't build any settings UI; you just listen for the keys you support and apply them.

What "registering" actually does. The portal menu always shows the standard controls, but the ones your game hasn't claimed appear greyed out with a "this game doesn't support X" note. Calling Legion.SDK.settings.listen(key, …) for the first time sends the portal a legion_settings_register message that enables that control. So: listening for a key is how you turn its slider/toggle on in the menu. Five keys are gated this way — master_volume, music_volume, graphics_quality, camera_sensitivity, show_fps. Register late and the control enables live; the menu doesn't have to be closed.

Wire up settings in three steps

  1. Listen for each key you support right after init

    One listen() per setting. The callback fires immediately with the current value (a default until the portal's real value lands), then again on every change. Registering also un-greys the control in the menu.

  2. Apply the value — remember it's a string in the callback

    parseInt(v,10)/100 for volumes, string-compare === 'true' for toggles, a switch for graphics_quality.

  3. Call triggerAll() once your systems exist after load

    This re-fires every listener with the current value, guaranteeing your audio, graphics, etc. all start in sync with the player's saved settings even if they were created after the first push arrived.

Game lifecycle & rooms #

The Legion.SDK.game namespace is how your game talks to the portal about what it's doing: when it has finished loading, when a match starts, and which room the player is in. The portal uses these signals to dismiss the loading screen, record analytics, and let friends join the player. Every call here is a one-way postMessage to the portal — they only do something when your game is embedded on bloxity.io (inside the iframe). On your own domain they are harmless no-ops, so it is always safe to call them.

The loading screen & loadingEnd() — read this first

This is the single most-misunderstood part of the SDK, so here is exactly how it works. The moment a player opens your game at bloxity.io/g/<slug>, the portal draws a full-screen loading overlay on top of your game's iframe (spinner + your game art). Your game is already running underneath — the player just can't see it yet. That overlay stays up until it is dismissed. There are two ways it can be dismissed, and which one applies depends on a single checkbox on your game's developer page: "LoadingEnd Support".

  1. Portal opens your game and shows the loading overlay automatic

    Nothing for you to do — the overlay is up from the first millisecond, covering the iframe while your assets download and your first frame renders.

  2. You report progress with loadingStep() optional, repeat

    Each call updates the small line of text at the bottom of the overlay ("Loading world…", "Connecting…"). Purely cosmetic, but it tells the player something is happening. Call it as many times as you like while loading.

  3. You call loadingEnd() exactly once when the game is ready after first frame

    This tells the portal "I'm done — take the overlay down." The overlay disappears and the player sees your game. This is also the moment the portal records that the game successfully loaded (a one-time POST /v1/games/<slug>/loaded analytics ping).

⚠ The trap that gets everyone. When "LoadingEnd Support" is ON for your game, the portal waits forever for your loadingEnd() call — there is no fallback timeout. If your game never calls it (or calls it before the SDK script has loaded, so the message is lost), the player is stuck staring at the loading spinner indefinitely. When the box is OFF (the default), the portal instead auto-dismisses the overlay 1.5 seconds after your frame first renders, whether or not you ever signal. So the box and the function call must agree. Turn the box on only once your game reliably calls Legion.SDK.game.loadingEnd().

The full truth table — find your row:

"LoadingEnd Support" boxDoes your game call loadingEnd()?What the player experiences
OFF (default)No✅ Overlay auto-hides 1.5 s after the frame renders. Fine for quick games, but if you're still loading at 1.5 s the player briefly sees an unfinished game.
OFFYes✅ Overlay hides the instant you call it, or at 1.5 s — whichever comes first. Recommended if you can't guarantee the call every time.
ONYes✅ Best UX. Overlay hides at exactly the right moment — never early, never late. Use this once your loading is deterministic.
ONNo❌ Stuck on the loading screen forever. This is the bug. Either add the call, or turn the box off.
One more condition: the portal only waits for loadingEnd() when your game also has SDK support enabled (the SDK Support toggle, on by default). A game with "LoadingEnd Support" on but SDK support off still takes the 1.5 s auto-dismiss path. In practice: both toggles on + a real loadingEnd() call = a clean, correctly-timed loading screen.

Bloxity owns the emote picker. The button in the in-game overlay, the wheel, ownership, prices, purchases and the rendered thumbnails are all rendered by the portal — your game never builds an emote menu. It registers once, then receives a single event: play this emote.

The button only appears over games that have registered, so nothing changes for your players until you opt in, and a player can never be shown a control your game would ignore.

Playing it

How you implement playEmote(id) depends on your character rig.

If your game has its own emote animations, fetch the catalogue once and map by name. Simple, but an emote added to Bloxity later will not appear in your game until you add a mapping.

const { emotes } = await (await fetch('https://api.bloxity.io/v1/avatar/emotes')).json();
const byId = new Map(emotes.map(e => [e.id, e]));

function playEmote(id) {
  const emote = byId.get(id);
  if (emote) myAnimator.play(myClipFor(emote.name));
}

If your game uses the standard Bloxity avatar (player.glb), the clips apply directly and every emote works automatically, including ones added after your game ships. This is the option that scales.

Each emote carries a clip:

{
  "len": 1.4,           // seconds
  "loop": true,
  "tracks": {
    // bone: [[timeSec, xDeg, yDeg, zDeg], ...]
    "ArmR_Offset": [[0, -60, 0, -10], [0.25, -144, 0, -16], [1.4, -60, 0, -10]]
  }
}
  • values are degrees, and are deltas over the bind pose, not absolute
  • euler order is XYZ, right-multiplied onto the bone's bind quaternion
  • ease between keys with smoothstep: s = s * s * (3 - 2 * s)
  • clamp outside the key range; loop wraps on time % len
  • an unknown bone name is ignored, never an error
function sampleTrack(keys, t) {
  if (t <= keys[0][0]) return keys[0].slice(1);
  const last = keys[keys.length - 1];
  if (t >= last[0]) return last.slice(1);
  for (let i = 0; i < keys.length - 1; i++) {
    const a = keys[i], b = keys[i + 1];
    if (t >= a[0] && t <= b[0]) {
      let s = (t - a[0]) / (b[0] - a[0]);
      s = s * s * (3 - 2 * s);                       // smoothstep
      return [1, 2, 3].map(j => a[j] + (b[j] - a[j]) * s);
    }
  }
  return null;
}

// per frame, per bone
const v = sampleTrack(clip.tracks[bone.name], clipTime);
if (v) {
  bone.quaternion.copy(bindQuaternion[bone.name]);
  bone.quaternion.multiply(new THREE.Quaternion().setFromEuler(
    new THREE.Euler(v[0] * DEG, v[1] * DEG, v[2] * DEG, 'XYZ')));
}

Gotchas

  • Register as soon as init() resolves. Earlier is a silent no-op (no SDK global yet); later means a late button. If your platform layer wraps the SDK, make sure the wrapper awaits its own init before forwarding the call — optional chaining through a not-yet-loaded SDK fails without a single error.
  • Do not check ownership yourself. Bloxity only ever sends an id the player is entitled to. Duplicating the check is how the two drift apart.
  • Unknown id? Ignore it quietly. Never throw — an emote is cosmetic and must never be able to break a frame.
  • The catalogue grows. Do not hardcode ids or assume a count.
  • Stop on movement. An emote that keeps playing while the player walks looks broken.

Bux purchases (IAP) #

Bux is Bloxity's in-game currency. The model is deliberately server-authoritative so games can't be cheated and players can't be charged for nothing: your game only ever passes a sku (a product id) — never a price — and the server looks up the price from your game's IAP catalog, deducts the Bux, and confirms the sale to your backend via a webhook. If anything in that chain fails, the Bux are refunded automatically.

How a purchase actually flows

  1. Player clicks buy → you call requestPurchase(sku) client

    The SDK shows a confirm modal populated with the server's product name and price (you don't render it). Nothing is charged yet.

  2. Player confirms → Bloxity prices & deducts Bux server

    The server re-reads the price from your catalog and atomically deducts it. If the player is short, the flow opens a real-money top-up for the smallest covering package, then continues automatically.

  3. Bloxity calls your game server's webhook server → your server

    A signed POST with the transaction details (sku, user, amount, your metadata) lands on your fulfillment endpoint. This is the moment you actually grant the item.

  4. Your server grants the item and returns 2xx your server, ≤10s

    Add the gems / unlock the skin in your database, then respond 2xx. The grant is only considered final once you do.

  5. requestPurchase resolves { success:true, transactionId } client

    Reflect the grant in the game UI. Record the transactionId if you want an audit trail.

The safety net: if your server doesn't return 2xx within 10 seconds (after a couple of quick retries), Bloxity auto-refunds the Bux and requestPurchase resolves { success:false }. A missing, slow, or broken webhook can never leave a player out of pocket — but it also means no webhook = no grant, so wiring up your endpoint is not optional if you sell anything.

Implement your game server's webhook

If you sell anything, your backend needs one endpoint. Bloxity calls it after deducting Bux; you grant the item and answer 2xx.

  1. Expose a POST endpoint once

    e.g. POST https://your-server.com/api/legion-webhook. Register its base URL as your game's default webhook (or pass a per-purchase webhookUrl in requestPurchase's options).

  2. Verify the secret header every request

    When LEGION_WEBHOOK_SECRET is configured, reject any request whose x-legion-webhook-secret header doesn't match. Never grant on an unverified call.

  3. Deduplicate by transactionId before granting

    Bloxity retries on network errors and 502/503/504, so the same transactionId can arrive twice. Grant each one only once.

  4. Grant the item, then return 2xx within 10 seconds fast

    Use sku, userId, and your metadata to apply the grant, then respond 2xx. A 4xx fails fast (no retry) and refunds; a slow or 5xx response refunds after retries. See the exact payload.

If your game has "LoadingEnd Support" enabled on its developer page but never fires this, the player is stuck on the loading screen forever; if the box is off, the overlay auto-clears 1.5 s after the frame renders. Use SDK_LegionLoadingStep("…") during your load to show progress text. See Game lifecycle for the full truth table.

Auth handshake #

The bridge listens to onUserChanged, then authenticates the Bloxity identity against your own game server and forwards the resulting session to Unity.

text
Legion.SDK.auth.onUserChanged(user)
  ├─ user != null
  │    ├─ result = await Legion.SDK.auth.authenticateWithServer(GAME_AUTH_URL)
  │    │     (SDK POSTs { token: <bloxity JWT>, user } to YOUR server)
  │    ├─ valid game-server response?  (must contain user.legionId / selected_*)
  │    │     ├─ yes → SendMessage('AuthManager','ProcessJsonAfterLogin', JSON.stringify(result))
  │    │     └─ no  → reject (retryable)
  └─ user == null
       └─ SendMessage('AuthManager','Logout2')

Example endpoints (your server, not Bloxity): https://usa-1.gunblox.io/api/accounts/login/legion, https://usa-1.2v2.io/api/accounts/login/legion.

What your /login/legion endpoint must do

  • Accept the POST body { token, user } and verify the Bloxity JWT (confirm the user _id).
  • Upsert a local game user keyed by legionId (sync pfp/skin/hat/back from Bloxity).
  • Return your own session JSON — the presence of user.legionId is how the bridge knows it's a real game-server response (raw Bloxity avatar data is rejected):
jsonc
{
  "accessToken":  "<your game JWT>",
  "refreshToken": "<your refresh token>",
  "user": {
    "legionId": "...", "username": "...", "displayName": "...",
    "pfp": "/pfps/...", "selected_skin": "...", "selected_hat": "..."
    /* + gems, premium, whatever your game needs */
  }
}
No game server? Skip authenticateWithServer and read the Bloxity user directly from Legion.SDK.auth.getUser() / forward it to Unity yourself. The game-server handshake is only needed if your game keeps its own accounts.

Bux webhook payload #

After deducting Bux, the Bloxity API POSTs this JSON to your resolved webhook URL (metadata.webhookUrl → the IAP's webhookUrl → the game's default). Respond 2xx within 10 s to confirm the grant, or the Bux are auto-refunded.

jsonc
// POST https://your-game-server.com/api/legion-webhook
// Header: x-legion-webhook-secret: <LEGION_WEBHOOK_SECRET>   (when configured)
{
  "transactionId": "txn_1718600000000_a1b2c3d4",
  "userId":        "6602f1a2b3c4d5e6f7080910",
  "username":      "coolplayer42",
  "gameSlug":      "my-game",
  "sku":           "gems_500",
  "productName":   "500 Gems",
  "productPrice":  50,
  "metadata":      { "playerId": "p_123" },
  "timestamp":     "2026-06-17T12:00:00.000Z"
}
Verify the secret. When LEGION_WEBHOOK_SECRET is set, check the x-legion-webhook-secret header before granting anything. The grant is only final once you return 2xx.
Retries & idempotency. On a network error or a 502/503/504, Bloxity retries the webhook (short backoff), so the same transactionId can arrive more than once — key your grant on it and no-op duplicates. A 4xx is treated as a permanent rejection (no retry) and refunds immediately; a timeout or repeated 5xx refunds after the retries are exhausted. The whole exchange is bounded by the 10 s per-attempt timeout.
